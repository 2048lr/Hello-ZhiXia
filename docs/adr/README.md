## ADR-0001

**无中心架构：复杂度从服务端转移到每台客户端**

**结论** 不设中心数据服务器。用户数据不经过服务方，各端持有完整副本。

**代价（作者自己写明）** 复杂度从服务端转移到了每一台客户端 ——
这也是 `core-mesh`（协调层）被认为是「本项目真正的工作量所在」的原因。

**出处** `packages/core-mesh/src/index.ts`

## ADR-0003

**Agent 内核选 pi（MIT 许可）；但必须自建存储抽象与权限门**

**结论与理由**

- **自建存储抽象**：`pi-durable` 官方标注 Experimental、API 不保证兼容。
  直接依赖它会让升级风险扩散到全项目。
- **权限门**：pi **没有内置权限系统**，默认以启动用户的权限运行。
  因此本项目必须自己实现「默认拒绝 + 出站白名单」（另见 [open-questions #7、#8](../open-questions.md)）。
- **桌面壳选 Electron**：pi 是 Node.js + TypeScript 实现，放在 Electron 主进程里可以直接
  `import`，省掉 sidecar 进程与 RPC 桥接。代价是约 150MB 的包体。
- **备选路径**：Tauri + Node sidecar（走 pi 的 RPC 模式），包体更小，
  但要自己打包并管理 Node 运行时。若包体成为问题可重新评估。

**出处** `packages/core-agent/src/index.ts`、`apps/desktop/src/main.ts`

## ADR-0004

**发现机制：局域网 mDNS + 跨网 rendezvous**

**结论** 同一广播域内用 mDNS 自动发现；跨网时必须有事先约定的见面点（rendezvous）。

**理由** 「自动发现互联」只在同一广播域内成立。手机在 4G、PC 在家、Linux 在云上时，
三者物理上无法互相发现。

**服务方的职责边界（必须严格遵守）**

1. 交换设备之间的连接候选地址（rendezvous）
2. 在 NAT 打洞失败时转发**端到端加密**的流量（relay）

它**不持有任何用户数据，也无法解密任何流量**。

**隐私上必须如实说明的事** 服务方可见的**不是内容，而是元数据**：设备 IP、连接时间、
流量大小、大致使用频率。这是一个降级，**不能对外宣称「零数据接触」** ——
准确说法是「无法读取你的数据」。

**出处** `packages/core-mesh/src/index.ts`、`services/rendezvous/src/index.ts`

## ADR-0005

**不要拿 chord 的 `watch` 当同步协议**

**结论** 实时会话流可以用 `@earendil-works/chord`，但数据同步必须走 op log。

**理由** chord 的 `watch` 是**实时观看语义**：慢消费者会丢中间帧、重连不回放。
把它当同步协议会静默丢数据。

**出处** `packages/core-mesh/src/index.ts`

## ADR-0006

**Android 是瘦客户端 + 本地完整数据副本，不执行 agent**

**结论**

- ✅ 持有完整的结构化数据副本（笔记、日程、待办、会话记录）
- ✅ 可离线读写本地数据，无需任何节点在线
- ✅ 可接收与触发提醒（走系统级闹钟，不依赖 agent 常驻）
- ✅ 可发起对话请求（需要算力节点在线）
- ❌ **不执行 agent**，不运行 pi

**为什么不在 Android 上跑 pi** pi 需要 Node.js ≥ 22.19。Android 上内置 Node
（`nodejs-mobile`）技术上可行，但**即使内置了也解决不了根本问题**：Doze 模式与各厂商的
杀后台策略会让常驻进程无法存活。结果是「算力节点」名不副实，却要付出明显的维护成本。

**对同步协议的影响（这条很容易被忽略）** 不能期待 Android 周期性主动联网。
模拟器为此专门提供 `antiEntropy: false` 的「只响应、不主动发起对账」设备，
并有用例钉住它 —— 因为「对端也会主动发起」这个隐含前提在 Android 上不成立。

> 相关：`packages/core-sync/src/sim/simulator.ts` 中 anti-entropy 应答必须带上自己集合的
> 那段推理，直接由本 ADR 推出。

**技术选型未定** Capacitor / React Native / 原生 Kotlin 三选一，
**关键判据是闹钟可靠性**（见 [ADR-0011](#adr-0011)）。

**数据层并不因此简化** 瘦客户端指的是**不跑 agent**，不是**不参与同步**。
Android 仍需完整实现 op log、CRDT 合并、墓碑，因此直接依赖 `@hzx/core-sync`。

**出处** `apps/android/README.md`、`packages/core-sync/src/sim/simulator.ts`

## ADR-0009

**Schema 版本偏斜必须显式报错，不能静默按旧 schema 解释**

**结论** 当数据的 schema 版本**高于**本端已知的最新版本时抛错，提示先升级应用。

**理由** 直接按旧 schema 解释新数据会**静默损坏数据**。

**配套的三条硬性约定**（`schema.ts` 注释）

1. 迁移必须是**纯函数**：相同输入在任何设备上都必须产出相同结果，
   否则各设备迁移后的数据会分叉，且难以察觉。
2. 新设备必须能解析**任意历史版本**的数据 —— 迁移链必须从旧版本一路可达。
3. 迁移函数一旦发布**不可修改**，只能追加新版本。修改已发布的迁移会让
   「已迁移过的设备」和「尚未迁移的设备」得到不同结果。

**出处** `packages/core-sync/src/schema.ts`

## ADR-0010

**节奏：各端先跑通、互联最后做；但数据层第一天就共享**

**结论** 先让三端各自跑通，互联放到最后。

**代价（作者自己写明）** 最大代价是**同步问题的反馈周期很长**：网络分区、时钟偏移、
消息乱序、丢包这几类 bug 靠真机手测几乎不可能复现 —— 它们表现为「偶尔顺序错乱」，
而偶发不可复现正是最难排查的形态。

**因此** 建立确定性多节点同步模拟器被列为 P0（见 [open-questions #9](../open-questions.md)）：
把上述条件变成可注入、可重复的参数，**同一个种子必然得到同一份 trace**，
失败用例可以精确重放。

**配套** 「三端共用同一个数据层包」必须在第一天就定下来 —— 这正是 `@hzx/core-sync`
存在的原因，也是 [ADR-0006](#adr-0006) 里 Android 虽不跑 agent 却仍依赖它的原因。

**出处** `packages/core-sync/src/sim/simulator.ts`、`apps/android/README.md`

## ADR-0011

**提醒的投递下放给本地系统闹钟**

**结论** 定时归属用「确定性归属 + 幂等键」；**响铃由本地系统闹钟负责**，
不依赖 agent 常驻。

**影响（关键路径）** 三端的闹钟实现直接决定提醒可不可靠：

| 能力 | Windows | Linux | Android |
| --- | --- | --- | --- |
| 系统闹钟 | 任务计划程序 | systemd-timer / 桌面提醒 | AlarmManager |

对 Android 而言这条更是技术选型的**首要判据**：如果所选方案无法可靠注册系统级闹钟
（或被系统抑制），整个提醒功能就不可靠 —— 而提醒是日常助手的核心功能。

**出处** `packages/core-mesh/src/index.ts`、`packages/platform-adapters/src/index.ts`、
`apps/android/README.md`

## ADR-0012

**写权租约只保护副作用，不保护数据；幂等键；冲突可见**

**结论**

- **写权租约只保护副作用，不保护数据** —— 数据的合并靠 op log，不需要租约。
- **会话级租约**：同一会话同一时刻只有一个节点能驱动。
- **幂等键**：所有有副作用的工具调用必须携带 `idempotencyKey`。
- **冲突宁可可见，不可静默**：日程时间、金额这类数据的冲突**必须呈现在 UI 上**，
  而不是被 LWW 悄悄覆盖。

**出处** `packages/core-agent/src/index.ts`、`packages/core-mesh/src/index.ts`、
`packages/ui-shared/src/index.ts`

## ADR-0014

**两级删除语义**

**结论** 删除分两级。

**理由** 在无中心的全量复制系统里，「删除」是一个分布式问题：
物理删除会让**离线设备重连后把数据复活**，所以删除必须写墓碑；
但墓碑不能永久保留（与 [ADR-0013](#adr-0013) 的体积预算冲突），所以需要第二级「彻底删除」。

**能兑现的承诺与不能兑现的承诺，必须明确区分开**

| 主张 | 能否 100% 兑现 |
| --- | --- |
| 服务方任何时候都无法读取你的数据 | ✅ 可以（只转发密文） |
| 删除后数据在所有地方彻底消失 | ❌ 取决于设备是否在线 |

**墓碑保留期** 180 天，远大于「设备正常离线」的典型时长。
未到保留期一律不裁剪；裁剪早于「设备可能离线的最长时间」会导致数据复活。

**强制清除的诚实性要求** 强制清除会把长期离线的设备移出配对列表，
**它们上面的数据无法从物理上删除** —— 这一事实必须如实告知用户，不能用文案掩盖。

**UI 要求** 如实展示「N 台设备尚未确认彻底删除」，
**不能把「已请求」显示成「已彻底消失」**。

**出处** `packages/core-sync/src/deletion.ts`、`packages/ui-shared/src/index.ts`
