## 问题 9：同步问题的反馈周期 —— **已解决**

**问题** [ADR-0010](./adr/README.md#adr-0010) 选择了「各端先跑通、互联最后做」的节奏，
其最大代价是**同步问题的反馈周期很长**：网络分区、时钟偏移、消息乱序、丢包这几类 bug
靠真机手测几乎不可能复现 —— 它们表现为「偶尔顺序错乱」，
而**偶发不可复现正是最难排查的形态**。

**处置** 曾被**升为 P0**。

**结果** 已由**确定性多节点同步模拟器**解决（`@hzx/core-sync/sim`）：

- 时间：整数虚拟毫秒，由 `run()` 推进，不读墙钟
- 随机：按种子驱动的 mulberry32，不调用 `Math.random()`
- 调度：消息按 `(dueAt, seq)` 排序投递，结果与插入顺序无关
- 传播：本地写入时向所有对端 push；另有周期性 anti-entropy 对账修复丢包与分区
- 对账：交换**完整 opId 摘要**（O(n) 但无条件正确）

**关键性质** 同一个种子必然得到同一份 trace（`sim.traceDigest()`），
因此任何一次失败的测试都可以被**精确重放**。

**刻意没做的事** 网络层只模拟「送达 / 丢弃 / 延迟 / 乱序」，
不模拟带宽、分片、加密与握手 —— 那些属于协调层的实现细节，用真机或集成测试验证更合适。

**出处** `packages/core-sync/src/sim/simulator.ts`、`packages/core-sync/src/sim/random.ts`

## 缺口 10：`OpLog` 没有快照 / 压缩能力

**现状** [`OpLog`](../packages/core-sync/src/op.ts) 接口只有 `append` / `all` / `since` /
`has` / `size`；全仓库只有一个内存实现 `createMemoryOpLog`，
其注释自己写明「生产环境应换成持久化实现」。

**为什么必然会撞上**（不是「可能」，是「一定」）

- [ADR-0013](./adr/README.md#adr-0013) 存在体积预算，且墓碑保留期就直接受它约束
  （`deletion.ts` 的注释点了这条）。
- 日志**只追加、不收缩**。`all()` 每次调用都对全部操作排序，`since()` 同样；
  `opsMissingFrom` 的对账摘要带宽是 O(n)。操作越多，这三处一起线性恶化。
- 每台设备持有**全量副本**，而个人助手是要常年运行的 —— 日志增长没有上限。

**任何方案都必须满足的约束**（从既有决策推出，不是我的偏好）

1. **幂等**：同一条操作重复投递不产生副作用（`op.ts` 的合并契约）。
2. **与到达顺序无关**：合并结果只取决于最终收到了哪些操作。
3. **不能与墓碑裁剪打架**：被 pin 住的墓碑不能丢（`deletion.ts`）。
4. **必须保住「对端还缺哪些操作」的判断能力**。这一点是真正的难点：
   `opsMissingFrom` 刻意用**完整 opId 摘要**而不是「最大 HLC 水位」，
   理由写得很清楚 —— 水位在丢包与乱序下会漏数据（设备先收到 h3、错过 h2，
   水位停在 h3，h2 就永远补不回来）。压缩掉操作之后，如何继续满足这条，是设计的核心。
5. **快照自身也受 schema 版本化约束**：迁移是纯函数、且迁移链必须从任意历史版本可达
   （`schema.ts`）。

**为什么没有直接写接口** 压缩之后的对账语义**直接决定 `core-mesh` 同步协议的形态**，
而 [ADR-0010](./adr/README.md#adr-0010) 明确把「互联」放在最后做。
在这里先定接口，等于反过来把协议设计锁死。**建议与 `core-mesh` 一起设计。**

## 缺口 11：没有任何冲突表达类型

**现状** `op.ts` 提供了 `Reducer` 与 `foldOps` 两个插槽，但仓库里
**没有任何实体 reducer**，也没有任何类型能表达「两个并发写入冲突了」。

**为什么需要** [ADR-0012](./adr/README.md#adr-0012) 与 `ui-shared` 的要求是明确的：
**冲突宁可可见、不可静默**，日程时间、金额这类数据的冲突**必须呈现在 UI 上**，
而不是被 LWW 悄悄覆盖。没有冲突类型，UI 层就无从呈现 ——
这条要求目前**只写在注释里，没有任何类型支撑**。

**为什么没有直接写接口** 冲突的**形状**取决于实体模型：哪些字段可以 LWW、
哪些应该取并集、哪些必须交给人选。而实体模型目前**完全不存在**
（连一个 reducer 都没有）。此时定下 `Conflict` 类型，会得到一个
既没有生产者、也没有消费者的死类型，并且很可能与真正的实体模型不匹配。
**建议与第一批实体 reducer 一起设计。**

**如果作者希望先要接口**：可以先只定「冲突发生的位置 + 参与冲突的操作 + 是否已自动解决」
这三样，把**解决策略**完全留给实体自己决定 —— 这样不会锁死任何策略选择。
本 PR 没有替你写，是因为连「位置」用什么寻址（字段名？路径？JSON Pointer？）
都取决于实体模型。
