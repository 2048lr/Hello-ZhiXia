# ADR-0001：采用 local-first P2P mesh 拓扑

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

项目要求「跨平台同步使用」，但对拓扑没有先验约束。有三种基本形态可选：

1. **中心化服务端** — 所有数据存在我们的服务器上，各端是客户端
2. **客户端-服务器（自托管）** — 用户自己跑一台服务器，各端连它
3. **local-first P2P mesh** — 每台设备都是节点，数据全量复制，无中心

需求侧给出了明确信号：用户希望「各端都是算力节点，自动发现互联，任何一台关闭都不会影响整体运行」，且「各个用户的使用都是独立的，不经过我的服务器」。这直接排除了形态 1，并强烈指向形态 3。

## Decision

采用 **local-first P2P mesh**：

- 用户数据以全量复制的方式存在于用户自己的每台设备上
- 设备之间自动发现、直连、端到端加密传输
- 不存在持有用户数据的中心服务器
- 允许一个**只做地址交换与密文中继的见面点**存在（见 [ADR-0004](./0004-rendezvous-and-relay.md)）

## Consequences

**正面**

- 隐私承诺可以做到最彻底：服务方在技术上无法读取用户数据
- 没有中心意味着没有中心化的故障域、没有数据泄露的集中风险、没有按量计费的运营成本
- 离线可用是天然属性，不是额外功能
- 用户对自己的数据有完全控制权

**负面**

- **复杂度从服务端转移到了每一台客户端**。同步、冲突解决、发现、打洞、租约、故障恢复全部要在客户端实现
- 没有权威时钟、没有权威状态、没有唯一调度者——这三样恰好是「提醒」与「不重复副作用」的必需品
- 数据一致性只能做到最终一致（受 CAP 约束，见 [ADR-0005](./0005-crdt-sync-basis.md)）
- 运维责任部分转移给用户（自托管见面点、故障排查、数据备份）
- 没有崩溃上报，线上问题排查显著变难
- 数据删除是分布式问题，无法单方面立即生效

## Alternatives considered

**中心化服务端** — 实现最简单、体验最好、可做最强记忆检索。被否决，因为它与"数据不经过服务方"的核心诉求直接冲突。

**客户端-服务器（自托管）** — 用户自己跑一台服务器，各端连它。实现难度远低于 mesh，且仍有隐私保证。被否决，因为「任何一台关闭都不影响整体运行」——自托管服务器一旦关机，所有端全部失效，这与需求明确相悖。

**混合：桌面本地 + 移动远程连** — 全平台覆盖且在移动端省电省流量。暂不采用——它需要维护两套状态模型，复杂度最高而收益不明确。若将来移动端体验成为瓶颈，可作为 ADR 重新评估。
