# ADR-0008：设备身份用 Ed25519 密钥对 + 二维码/短码配对

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

P2P mesh 里没有中心化的账号系统（[ADR-0001](./0001-local-first-p2p-mesh.md)），因此「你是谁」「这台设备是否可信」必须由设备之间自行确立。

需要满足：

1. **不能依赖服务器**来判断身份（虽然见面点会参与地址交换，但绝不能让它成为信任仲裁者）
2. **首次配对必须能防中间人**——否则攻击者可以冒充用户的另一台设备
3. **普通用户要能完成**——配对流程不能要求理解公钥、指纹校验等概念
4. **配对是一次性的**——之后日常连接不应再打扰用户

## Decision

**每台设备生成一对 Ed25519 密钥**，并以此作为设备身份：

- 设备 ID = 公钥的哈希
- 私钥存放于操作系统钥匙串，**不落明文盘、不出设备**
- 用户身份同样是密钥对（"账号"就是一对密钥，不是用户名+密码）

**首次配对流程**：

1. 设备 A 生成一个**短期有效的配对凭据**（含会话密钥 + 过期时间），显示为**二维码**（含短码/数字口令作为降级手段）
2. 设备 B 扫描二维码，两端据此建立一条**带认证的加密通道**
3. 两端**交换并持久化彼此的公钥**，此后互相信任
4. 之后所有连接都基于已交换的公钥做认证，**不再需要见面点参与信任判断**

**多设备一致性**：设备 C 加入时，只需与**任意一台已配对设备**配对，随后通过已建立的信任链获得其他设备的公钥——不需要与每台设备逐一配对。

## Consequences

**正面**

- **彻底不需要服务器参与身份判断**，见面点在信任模型中被降级为纯粹的地址簿
- 密钥即身份，天然支持「多个用户各自独立」——不需要注册、不需要用户名唯一性检查
- Ed25519 密钥短、签名快，适合移动端
- 二维码配对对普通用户友好，且防中间人的强度足够（前提是二维码通过可信物理渠道传递）
- 用短码作为降级手段，覆盖没有摄像头或不愿用摄像头的场景

**负面**

- **密钥丢失即身份丢失**。用户换机、重装系统、清除钥匙串后，旧身份无法恢复——除非实现了密钥备份/导出机制（**这是一个必须在实现前回答的问题**）
- 需要妥善设计配对凭据的有效期，过长则安全性下降，过短则用户来不及操作
- 短码方案的安全性弱于二维码（可被暴力枚举），需要配合尝试次数限制
- 设备间的信任链传递意味着：一台设备被攻陷，可以引入一台恶意设备。需要提供「查看并移除已配对设备」的界面
- 「移除设备」后，被移除设备仍可能持有历史数据（数据已复制到它上面）。需要如实告知用户这一点

## Alternatives considered

**中心化账号系统** — 体验最好，用户用邮箱密码登录即可。被否决：需要一个身份服务器，与 [ADR-0001](./0001-local-first-p2p-mesh.md) 冲突。

**仅靠见面点做设备发现与认证** — 实现简单。被否决：见面点将变成事实上的信任仲裁者，一旦它被攻陷或被要求配合，整个安全模型崩塌。

**纯数字配对码（无二维码）** — 实现最简单。作为**降级手段**保留，但不作为主路径：数字码熵低，需要额外的尝试限制与速率限制才能达到可接受的安全性。

## 备注

**密钥备份问题未决**。在 local-first 且无服务器的前提下，密钥备份只能靠用户自己承担（导出恢复短语），或者接受「换机即重新配对」。这需要产品层面的取舍，建议在实现配对流程之前先定下来。
