# ADR-0014：两级删除语义与诚实的隐私承诺

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

在无中心的全量复制系统里，「删除」是一个分布式问题：

- 物理删除会导致**离线设备重连后把数据复活**（[data-model.md](../data-model.md#四删除墓碑tombstone) 已确定用墓碑解决）
- 但墓碑不能永久保留，否则元数据无限增长
- 而用户对「删除」的期待是**立刻、彻底、不可恢复**——这与分布式系统能提供的保证之间存在落差

核心矛盾：**如果对用户承诺"删了就彻底没了"，而实际做不到，那么这就是一个虚假的隐私承诺。** 对于一个主打隐私的产品，虚假承诺的代价远高于承认限制。

本项目的隐私主张有两句，它们的可兑现性**完全不同**：

| 主张 | 能否 100% 兑现 |
| --- | --- |
| 「服务方在任何时候都无法读取你的数据」 | ✅ **可以**。服务方只转发密文，技术上无法解密 |
| 「删除后数据在所有地方彻底消失」 | ❌ **取决于设备是否在线**。无法无条件保证 |

## Decision

采用**两级删除语义**，并把可兑现与不可兑现的部分明确区分。

### 一级 · 普通删除（默认行为）

- 写墓碑，**墓碑保留 180 天**
- 180 天后由快照裁剪清除
- **如实告知用户**：离线超过 180 天的设备重连时，其上的旧数据可能被复活

180 天这个取值的依据：远大于"设备正常离线"的典型时长（出差、闲置、维修），同时避免墓碑无限积累。

### 二级 · 彻底删除（用户主动触发）

1. 生成 `purge.request` 指令，广播给**所有已知设备**（配对列表中的设备）
2. 全部确认后：**全端物理删除**数据、关联墓碑，并从快照中剔除
3. 若存在长期离线设备，UI 如实显示「**N 台设备尚未确认**」，并提供两个选项：

| 选项 | 语义 |
| --- | --- |
| **等待** | 数据在这些设备上线前仍可能存在。明确告知 |
| **强制清除** | 将这些设备从配对列表移除，标记为「需重新配对才能加入」。**已在它们上面的数据无法从物理上删除**，必须如实告知 |

### 隐私说明的措辞原则

**可以说**（且在技术上可验证）：

> 我们（服务方）在任何时候都无法读取你的数据。你的数据只存在于你自己的设备上，我们看到的只有加密流量与连接元数据。

**不可以说**：

> 删除后数据在所有地方彻底消失。

**应当说**：

> 删除会在你自己的设备之间同步。如果某台设备长期离线，它会在你重新连接该设备后才完成删除。

## Consequences

**正面**

- 删除语义明确，用户知道自己在做什么选择
- 隐私承诺**句句可兑现**，这在隐私类产品里是核心资产
- 「强制清除」提供了兜底路径，不会因为一台丢失的设备而卡住
- 180 天墓碑期让"普通删除"在绝大多数场景下表现正常

**负面**

- **"彻底删除"在有离线设备时不能立即完成**，这与用户的直觉期待不符，需要 UI 与文案把这件事讲清楚
- 需要维护配对设备列表与其在线确认状态，是一个额外的状态机
- 「强制清除」后残留数据在物理上仍在被移除的设备上，**存在真实的隐私风险**（例如丢失的手机），只能如实告知，无法技术上解决
- 180 天是估算，过长会让墓碑积累，过短会让复活的概率上升
- 快照裁剪是破坏性操作，实现出错会导致墓碑丢失进而数据复活，需要仔细测试

## Alternatives considered

**只有物理删除，不用墓碑** — 最简单，用户直觉最符合。被否决：离线设备必然复活数据，这是 [data-model.md](../data-model.md) 已经论证过的问题。

**墓碑永久保留** — 彻底避免数据复活。被否决：元数据无限增长，与 [ADR-0013](./0013-knowledge-base-scale.md) 的体积预算冲突。

**无条件承诺"彻底删除"** — 产品文案最漂亮。被否决：做不到。对一个以隐私为核心卖点的产品，虚假承诺一旦被发现，损失的是整个产品的可信度。

**不做彻底删除，只提供导出** — 实现最简单。被否决：用户有权要求删除自己的数据，尤其在设备丢失或转手时。
