# ADR-0007：模型走云端 API，每端各自持凭据

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

两个相互纠缠的问题：

**问题一：模型从哪来？**

| 方案 | 能力 | 隐私 | 离线 |
| --- | --- | --- | --- |
| 全部云端 API | 最强 | 数据出设备 | 不可用 |
| 全部本地模型 | 明显受限，Android 上基本跑不动 | 最强 | 可用 |
| 混合路由 | 需要做模型路由 | 视路由而定 | 部分可用 |

**问题二：API 凭据放哪？**

在 local-first mesh 里，凭据的存放方式有几种选择，且它和「安装即用」的目标存在直接冲突——**普通用户不会为了用一个助手去注册 provider 账号、申请 API key、再在每台设备上各填一遍。**

同时必须承认一个事实：**即使拓扑是去中心化的，LLM 调用本身仍是中心化的外部依赖。** 发起 run 的那台设备若中途关机，这次 run 就断了。

## Decision

**模型供给**：全部走云端 API，不做本地模型路由（pi 的 llama.cpp 能力保留但不作为默认路径）。

**凭据持有**：

- 用户在**任意一台设备上输入一次** API key
- 该 key 作为一条用户数据，经**端到端加密通道同步**到用户自己的其他设备
- 落盘时进入**操作系统钥匙串**（Windows Credential Manager / libsecret / Android Keystore），不明文落盘
- **静态时每台设备各持一份**——这正是「每端各自持 key」的字面含义，但用户只需输入一次

**凭据不经过服务方**：见面点只转发密文，无法解密凭据。

## Consequences

**正面**

- 模型能力上限最高，且不需要我们承担推理成本——成本直接由用户与其 provider 结算
- 不需要做模型路由，省掉一整个模块
- 对齐「不经过我的服务器」：连模型调用都不经过我们
- 「输入一次」满足了安装即用的体验要求

**负面**

- **离线不可用**。没有网络时 agent 完全无法工作（数据仍可读写，因为数据是本地的）
- 用户自行承担 API 费用，对成本敏感的用户是门槛；需要提供用量统计与熔断（见 [open-questions #10](../open-questions.md)）
- 用户需要自行注册 provider 账号——虽然只做一次，仍是安装流程中最重的一步
- 凭据在用户的多台设备上都存在，**每台设备都是一个潜在的泄露面**。设备丢失、恶意软件都会危及凭据，这比「凭据集中在服务端」的风险面更大（虽然后者风险更集中）
- 需要设计凭据轮换与吊销流程
- run 中途设备关机 → 该次 run 中断，需要设计可续跑的语义（pi-durable 的事务化提交对此有帮助）

## Alternatives considered

**每台设备各自手动输入** — 安全性略高（凭据不经网络传输）。被否决：与「安装即用」直接冲突，普通用户无法接受在每台设备上重复操作。

**我们提供统一 API 代理并计费** — 用户体验最好，无需任何 provider 账号。被否决：这会让**所有请求经过我们的服务器**，与 [ADR-0001](./0001-local-first-p2p-mesh.md) 的核心隐私承诺直接冲突；同时我们承担推理成本与合规责任。

**全部本地模型** — 隐私最强、无网络依赖。被否决：日常助手需要的理解与生成能力，本地小模型在 Android 上无法提供；且这与「安装即用」也冲突（需要用户自行配置模型文件与推理环境）。

## 相关

- pi 的统一多 provider API（`@earendil-works/pi-ai`）使 provider 切换成本很低，本决策在 provider 层面**不锁定**任何厂商
