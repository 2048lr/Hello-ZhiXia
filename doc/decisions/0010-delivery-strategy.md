# ADR-0010：交付策略——各端先独立跑通，数据层第一天共享

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

需求方给出的开发节奏是：

> 先做各端最小可行个体，最后再做各端的互联，同样在进行开发时可以借鉴其他各端的经验。

这个节奏有明确的好处：早拿到可用的东西、验证价值、避免长时间没有产出。三端并行开发时，一端的经验可以快速惠及其他两端。

但它有一个前提需要检验：**互联究竟能不能"最后再做"？**

答案是**一半可以，一半不可以**。把待办事项分成两类：

| 类别 | 内容 | 能否推迟 |
| --- | --- | --- |
| **传输层** | 发现、NAT 打洞、中继、配对 UI、在线状态、写权租约 | ✅ 可以。推迟不会造成返工 |
| **数据层** | 标识符、逻辑时钟、写入方式、删除语义、schema 版本化、代码共享 | ❌ 不可以。推迟等于三端一起重写 |

原因很直接：**同步不是最后"加上去"的功能，而是数据模型的性质。** 如果三端先按普通本地 App 的写法（SQLite + 直接增删改查）各自实现，到互联时会发现：写入方式、主键、时间戳、删除语义全都无法表达并发，全部需要重写。

代价的一侧是明确的：这六件事加起来前期多花不了多少力气——用 ULID 而不是自增主键、写 op log 而不是直接改字段、时间戳走 HLC——都是**换个写法**，而不是多做一个模块。

## Decision

**保留需求方的开发节奏，但把数据层从"最后再做"里拿出来，放到第一天。**

具体执行：

1. **第一天就建立 monorepo 与共享数据层包**（`packages/core-sync`），三端共用
2. **数据层的约定立即生效**，见 [data-model.md](../data-model.md)：ULID、HLC、op log、墓碑、schema 版本化
3. **传输层可以最后做**：发现、打洞、中继、配对 UI、在线状态、写权租约
4. **各端可以只跑单机**：在协调层完成之前，三端各自独立可用，不依赖网络
5. **共享代码即"借鉴经验"**：三端共用一个数据层实现，一端踩过的坑，另两端天然不会踩

## Consequences

**正面**

- 保留了「早拿到可用产出」的节奏——各端在没有任何网络功能的情况下就能跑起来、被使用、被验证
- **互联那一步不会返工**。传输层是纯增量：在已有 op log 之上加"把 op 发给别的设备"即可
- 三端数据模型天然一致，不存在互相无法解析的风险
- 各端的经验通过**代码**而非**文档**传递，保真度最高
- 单机可用意味着开发期完全不需要协调层，可以在没有服务器的情况下开发很久

**负面**

- **前期多了一层抽象的认知成本**。开发者会觉得"我就存个笔记，为什么要搞 op log 和 HLC"
- 前期无法验证同步逻辑是否真的正确——直到互联阶段才会发现问题，反馈周期较长
- 如果最终产品方向发生根本变化（例如改为中心化服务端），这层数据设计会变成负担
- 共享数据层包需要被三端同时依赖，任一端的特殊需求都可能污染共享包的设计（需要克制）

## Alternatives considered

**完全按需求方原始节奏（互联最后做，数据层也最后做）** — 前期最快，前期认知负担最低。被否决：互联阶段需要重写三端的数据层，总工作量反而更大，且返工发生在项目后期（风险最高的时间点）。

**先做单机版验证价值，再决定是否多端** — 风险最低的探索方式。被否决，但**部分吸收**：本决策的第 4 点（各端可只跑单机、不依赖网络）实际上就是这个思路，只是数据层不跟着"简化"，因为数据层一旦简化，后期的迁移成本远高于前期多写的成本。

**一开始就做全网状互联** — 能最早验证同步。被否决：协调层是最难的部分，一开始就做会让「拿到可用产出」遥遥无期，也失去了"各端先跑通"的节奏优势。
