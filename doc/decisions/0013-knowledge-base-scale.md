# ADR-0013：知识库规模上限与降级阈值

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

[ADR-0001](./0001-local-first-p2p-mesh.md) 选择了多设备全量复制结构化数据。这个承诺能否兑现，完全取决于数据会长到多大——而当时的讨论没有量化过。

关键区分（来自 [data-model.md](../data-model.md)）：**「全量复制」只适用于结构化数据，不适用于二进制内容。** 本决策把这个区分量化成可执行的预算。

## Decision

### 设计目标

| 项 | 目标上限 |
| --- | --- |
| 结构化条目数 | **10 万条**（笔记、日程、待办、会话、提醒等） |
| 结构化数据体积 | **200 MB**（不含二进制） |
| 附件 / 二进制总量 | **50 GB**（但不全量复制） |
| 单设备本地附件缓存 | **2 GB**（LRU，用户可调） |

### 各类数据的具体策略

**结构化数据（全量复制）**

- 10 万条 × 平均 2 KB ≈ 200 MB
- 加上 op log、墓碑、索引，实际约 **3–5 倍 → 约 1 GB**
- 桌面端无压力；Android 端需要**压缩 + 快照裁剪**，属于可接受范围

**二进制内容（永不参与全量复制）**

- 内容寻址存储（按哈希命名）
- 按需拉取 + LRU 缓存（默认上限 2 GB）
- 用户可对特定条目标记「离线可用」，强制常驻本地

**PDF / 图片的文本抽取**

| 类型 | 处理 |
| --- | --- |
| PDF 文本层 | 抽取为**可合并文本**，进入结构化数据（可全量复制、可搜索） |
| 图片 OCR | 同上 |
| 原文二进制 | 仍按需拉取，**不因抽取过文本而变成全量复制** |

**向量索引（本地构建，从不同步）**

- 基于抽取出的文本在本地构建
- 同步它既昂贵又易错，且可确定性重建

### 降级阈值

当**结构化数据超过 200 MB** 时，自动切换到「元数据全量 + 正文按需」模式：

- 条目标题、标签、时间、关系仍然全量复制
- 正文分片，按需拉取
- **必须明确告知用户已进入降级模式**，而不是静默改变行为

## Consequences

**正面**

- **承诺变成可量化的**：10 万条 / 200 MB 是可以压测、可以监控的数字，而不是"应该够用"
- 附件与结构化数据彻底解耦，二进制不会阻塞同步
- 降级路径明确——数据增长不会导致同步崩溃，而是平滑切换到按需模式
- 文本抽取让 PDF 与图片"可搜索但不必常驻"，兼顾了检索能力与存储成本

**负面**

- **10 万条与 200 MB 是估算，不是实测**。必须在早期用真实数据做压测验证，否则这个阈值可能定错了
- Android 上约 1 GB 的结构化数据仍不算小，低端机型可能吃紧
- 「正文按需」模式在离线时体验明显下降（能搜到但打不开）
- 降级需要用户理解，UI 与文案有成本
- 附件 LRU 淘汰会导致"明明看过的文件又要重新下载"，需要预取策略配合（见 [open-questions #6](../open-questions.md)）

## Alternatives considered

**不设上限，永远全量复制** — 实现最简单，语义最纯粹。被否决：数据增长是必然的，没有降级路径意味着同步最终会崩，而且是在用户数据已经很多、最难迁移的时候崩。

**全量复制 + 二进制也全量** — 语义一致性最好（任一台设备都有完整副本）。被否决：50 GB 的二进制在移动网络上同步一遍是不可接受的，且手机会直接爆存储。

**所有正文都按需，不分级** — 实现更简单统一。被否决：日常使用中绝大多数笔记很小很常用，把它们也做成按需拉取会让"打开笔记"这个最高频操作带上网络延迟，体验损失远大于收益。
