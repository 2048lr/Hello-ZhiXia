# ADR-0012：写权租约保护的是「副作用」，不是「数据」

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

pi-durable 的文档明确写着：

> One process owns a storage at a time; there is no cross-process locking.

因此多设备同时写同一份存储是未定义行为，需要租约来串行化。

但这里有一个容易走偏的地方：**如果对"所有写操作"都上租约，就等于放弃并发**——同一时刻只有一台设备能干活，而 mesh 的价值恰恰在于多端都能用。

重新审视会发现，需要串行化的从来不是"写"，而是**有副作用且不可合并的操作**：

| 操作 | 可合并？ | 有副作用？ | 需要租约？ |
| --- | --- | --- | --- |
| 写一条笔记 | ✅ CRDT | ❌ | ❌ |
| 改一个日程 | ✅ CRDT | ❌ | ❌ |
| 执行一次 agent run（会调用工具） | ❌ | ✅ | ✅ |
| 定时触发提醒 | ❌ | ✅ | ✅ |
| 上传附件 | ✅ 内容寻址天然幂等 | ❌ | ❌ |
| 重建向量索引 | ❌ | ✅（烧钱） | ✅ |

## Decision

**租约按对象分粒度，且只保护副作用。**

| 对象 | 租约粒度 | TTL | 说明 |
| --- | --- | --- | --- |
| agent run（会话执行） | **会话级** | 60 秒，执行中续租 | 同一会话同一时刻只有一个节点能驱动 |
| 定时仲裁角色 | **全局独占** | 30 秒 | 见 [ADR-0011](./0011-reminder-exactly-once.md) |
| 向量索引重建 | **每索引一份** | 按重建时长 | 防止多端重复烧 embedding 费用 |
| 写笔记 / 日程 / 待办 | **无租约** | — | 走 CRDT 合并 |
| 附件上传 | **无租约** | — | 内容寻址，重复上传是幂等的 |
| 提醒投递 | **无租约** | — | 已下放到本地系统闹钟 |

### 副作用的幂等保护

租约只保证"不会同时执行"，不保证"不会执行两次"（租约过期、崩溃重试都会导致重复）。因此所有有副作用的工具调用必须携带幂等键：

```
idempotencyKey = hash(runId + toolCallSeq + args)
```

- **执行前**查本地已执行记录
- **执行后**记录结果（作为一条 op，跨设备共享）

这样即使两个节点因租约交接而都执行了，第二次会被幂等记录拦住。

**注意**：幂等记录本身是 op，也有同步延迟。租约负责把重复的概率降到很低，幂等负责把剩下的重复变成无害——两者缺一不可。

## Consequences

**正面**

- **并发度显著提高**：纯数据写入完全无锁，多端可以同时编辑笔记、日程、待办
- 接口清晰：「这个操作需要租约吗？」等价于「它有副作用吗？」，判断标准单一且可解释
- 与 CRDT 的分工明确：可合并的走 CRDT，不可合并的走租约

**负面**

- **需要准确分类每个操作**。把有副作用的操作误判为「可合并」会导致重复副作用（例如发两封邮件）；把纯数据操作误判为「需要租约」会无谓降低并发。这个分类是**必须逐操作审查**的
- 续租失败的处理逻辑复杂：继续执行（可能重复）还是中止（可能半途中断）？
- 租约依赖时间判断，需要 HLC + 单调时钟配合，不能用墙钟
- 幂等记录的无限增长需要清理策略（可随快照裁剪）
- 全局独占的仲裁角色在节点频繁上下线时会产生租约抖动

## Alternatives considered

**全局单写者** — 实现最简单，绝对安全。被否决：同一时刻只有一台设备能执行任何操作，多端体验退化到"要等另一台闲置"，浪费了 mesh 的架构优势。

**资源级租约（细到每条记录）** — 并发度最高。被否决：实现复杂、死锁风险高、且收益有限——因为真正需要串行的副作用操作（agent run）本身粒度就是会话级，细到记录级没有实际收益。

**完全依赖幂等，不用租约** — 架构最简单。被否决：幂等能防重复，但防不住**并发执行同一件事**造成的资源浪费与中间态冲突（例如两个节点同时跑同一个 agent 会话，会各自调一遍 LLM、各自执行一遍工具）。
