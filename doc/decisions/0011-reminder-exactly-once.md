# ADR-0011：提醒的「恰好一次」归属算法

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

无中心 mesh 里没有天然的唯一调度者：

| 策略 | 后果 |
| --- | --- |
| 所有节点都调度 | 用户收到 N 次提醒（N = 在线设备数） |
| 只有一个节点调度，而它关机 | 完全收不到 |

提醒又是日常助手的**核心功能**，漏触发不可接受。

但这里有一个关键的观察改变了整个问题的性质：**如果"触发"是幂等的，那么"重复触发"就是无害的噪音，而不是错误。** 一旦接受这一点，就不必再追求分布式系统里最难保证的 exactly-once，只需要保证 at-least-once + 幂等过滤。

## Decision

采用**三层结构**，核心是**把「响铃」与「去重」彻底分离**：

### 第一层 · 投递层（决定"会不会响"）

**由每台设备本地的系统级闹钟负责**，不依赖任何远程节点。

- Windows：任务计划程序 + 系统通知
- Linux：systemd-timer / 桌面环境提醒 + 通知
- Android：`AlarmManager` + 通知

设备在**注册或修改提醒条目时**，就在本地把闹钟排好。此后无论仲裁者在不在线、无论网络通不通，闹钟都照常响。

### 第二层 · 仲裁层（决定"有没有重复"）

所有**在线算力节点**按 `deviceId` 字典序排序，**ID 最小者**担任「定时仲裁者」：

- 在提醒到达时向 op log 写入一条 `reminder.fired` 事件（带 `reminderId`）
- 仲裁权通过**心跳租约**持有，TTL = 30 秒，未续租则失效
- 仲裁者离线后，下一个 ID 最小的在线节点在 TTL 过期后接管

### 第三层 · 幂等层（决定"要不要忽略"）

- 每条提醒有全局唯一的 `reminderId`
- `reminder.fired` 事件携带该 ID
- 每台设备维护"已触发集合"，收到重复触发**直接丢弃**

### 响铃设备的选择

为避免"三台设备一起响"的吵闹体验，默认策略：

1. 用户显式指定的「响铃设备」优先
2. 未指定时，选择最近 5 分钟内**有用户活动**的设备
3. 其余设备**只记录触发、不发出声音**（静默通知）

## Consequences

**正面**

- **漏触发几乎不可能**：投递层是本地系统闹钟，不需要任何网络或对端在线
- 仲裁者离线**不影响响铃**，只影响去重的及时性
- 幂等让「重复」降级为可接受的噪音，从而消除了 exactly-once 这个分布式难题
- 交接窗口短（30 秒 TTL）也不会造成漏触发，因为投递不依赖仲裁者——这是一个由架构带来的自由

**负面**

- **短时间内的重复响铃不可避免**。幂等去重需要时间和网络，跨设备的"已响过"标记无法瞬时同步。用户可能遇到两台设备前后响铃
- 需要三套平台适配代码（三个系统的闹钟 API 差异很大）
- **依赖设备本地时钟准确**。用户设备时间偏差会直接导致闹钟不准。需要定期与 HLC 校准，并检测到显著偏差时提示用户
- 「响铃设备选择」策略需要产品层打磨，规则太死板会让用户困惑
- 需要额外的数据字段：`reminderId`、触发状态、响铃设备标记

## Alternatives considered

**纯仲裁者投递（仲裁者到点发推送）** — 语义最干净，只需一次投递。被否决：仲裁者离线即漏触发，而提醒漏触发是不可接受的失败模式。

**所有设备都投递，靠幂等去重** — 实现最简单。被否决：会先响 N 次再谈去重，用户体验很差。但本决策的第三层实际上吸收了这个思路，只是把"响"限制在单台设备。

**指定一台固定设备作为闹钟设备** — 规则简单。被否决：该设备关机即完全失效，回到了"漏触发"问题。
