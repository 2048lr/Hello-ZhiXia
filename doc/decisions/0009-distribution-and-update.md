# ADR-0009：自行分发安装包 + 应用内自动更新

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

需求方选择「安装即用」，但「安装即用」与分发渠道是两件事：前者指**装完之后不用配置**，后者指**用户怎么拿到安装包、怎么升级**。

候选渠道：

| 渠道 | 优势 | 代价 |
| --- | --- | --- |
| 官网 / GitHub Releases + 应用内更新 | 无审核摩擦、发布节奏自控、可灰度 | 用户会遇到系统安全警告；需要自建更新机制 |
| 应用商店（Microsoft Store / Google Play） | 用户信任度高、安装体验好 | 审核周期、合规成本；P2P + 读取用户数据类应用容易在审核中被质疑 |
| 包管理器（winget / apt / AUR） | 技术用户友好 | 覆盖面窄，且审核也有周期 |

## Decision

**自行分发安装包，配合应用内自动更新。**

- **Windows** — 提供安装器（NSIS / MSI）
- **Linux** — 优先 AppImage + 发行版包（deb / rpm）
- **Android** — 提供 APK 侧载；若后续上架商店，另开 ADR
- **更新机制** — 应用启动后检查更新源（官方发布地址），下载并校验签名，提示安装
- **签名** — 所有安装包必须签名；更新包必须验证签名后才允许安装

## Consequences

**正面**

- **发布节奏完全自控**——不需要等待审核，可以随时发紧急修复
- 可以做灰度发布、按需回滚
- 无需为应用商店的合规要求（隐私政策、数据安全声明、权限说明）做额外工作
- 不会被商店政策变动影响（例如商店突然收紧 P2P 或后台权限类应用的审核）

**负面**

- **用户会遇到系统安全警告**。Windows SmartScreen 会拦「未知发布者」，Android 会要求用户手动允许「安装未知来源应用」。这与「安装即用」的目标直接冲突，是**本决策最大的代价**
- 缓解渠道警告需要**代码签名证书**（Windows 的 EV 证书有成本且需要企业资质审核），这是必须提前规划的采购项
- **自动更新在无服务器的前提下需要解决分发托管问题**。官方发布地址本身就是一个可用性依赖，且更新元数据（谁在什么时间检查了更新）会暴露使用信息
- Android 侧载意味着无法自动更新整个应用（Android 不允许侧载应用静默自更新），需要引导用户手动安装新 APK，或改用「应用内下载 + 系统安装器」流程
- 没有应用商店带来的自然流量与信任背书

## Alternatives considered

**上架应用商店** — 信任度与安装体验最好。暂缓而非否决：审核成本与不确定性在项目早期难以承受，尤其是「读取邮件/文件 + 后台常驻 + P2P 连接」这些权限组合在审核中需要大量解释。待产品稳定后再评估。

**不做自动更新，只发新版本** — 实现最简单。被否决：同步协议与数据 schema 会持续演进，**版本偏斜**（不同设备跑不同版本）会导致同步失败或数据解析错误。自动更新是同步系统健康的必要条件，不是体验优化。
