# ADR-0004：自建 rendezvous / relay，默认公共节点 + 可自托管开关

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

[ADR-0001](./0001-local-first-p2p-mesh.md) 确定了 P2P mesh 拓扑，但回避了一个物理问题：

**「自动发现互联」只在同一个广播域内成立。**

| 场景 | 能否自动发现 |
| --- | --- |
| 两台设备在同一 Wi-Fi | ✅ mDNS / UDP 广播即可 |
| 手机在 4G，PC 在家 | ❌ 不在同一广播域，物理上无法互相发现 |
| Linux 在云上，PC 在家 | ❌ 同上 |

跨网络时，设备必须有一个**事先约定的见面点**：大家先连到它交换地址与候选，然后尝试点对点直连；打洞失败时由它转发密文。

于是产生一个三方矛盾：

| 想要 | 代价 |
| --- | --- |
| 安装即用 + 跨网络 | 必须由我们提供公网见面点 |
| 无中心 + 跨网络 | 用户必须自己搭见面点（普通用户做不到） |
| 安装即用 + 无中心 | 只能限定同一局域网 |

需求方选择了「公共 + 可自托管开关」。

## Decision

**自建一个只做地址交换与密文中继的 rendezvous / relay 服务**，部署策略为：

- **默认**：所有用户连我们运营的公共节点
- **可选**：高级用户可在设置中切换到自建节点
- **职责边界**：该服务**只**做两件事——交换连接候选地址、在打洞失败时转发端到端加密流量。它**不持有任何用户数据，也无法解密任何流量**

## Consequences

**正面**

- 「安装即用」与「跨网络」同时成立，普通用户零配置即可多设备互联
- 自托管开关保留了「完全不依赖服务方」的可能性，回应用户的主权诉求
- 隐私承诺仍然成立：服务方可见的只有 IP、连接时间、流量大小等元数据，**不是内容**

**负面**

- **我们从「纯软件」变成了「要运维一个在线服务」**。该服务的可用性成为整个产品跨网体验的前提
- 带宽成本由我们承担，中继流量占比越高成本越高
- 元数据仍然暴露：连接时间、设备 IP、大致使用频率。这是一个**必须如实写进隐私说明**的降级，不能宣称「零数据接触」
- 服务被打上「中心服务器」的标签，可能在用户认知上与 local-first 的承诺产生张力，需要清晰的解释
- 自托管模式的配置复杂度会成为部分用户的支持负担

## Alternatives considered

**用现成 overlay 组网（Tailscale / ZeroTier）** — 一天就能跑通，完全避开 NAT 穿透的所有坑。被否决：它把第三方引入了信任链，且要求用户额外安装客户端并注册账号，与「安装即用」冲突。不过它是很好的**开发期临时方案**——在协调层尚未完成时，可以用它快速验证同步逻辑。

**只做局域网互联** — 架构最简单。被否决：手机离开家即完全失联，「日常助手」的核心价值不成立。

**纯 P2P，不做中继** — 完全没有服务器。被否决：NAT 穿透存在相当比例的失败场景（对称 NAT、部分企业网络），没有中继兜底意味着相当一部分用户间歇性不可用，且故障无法解释、无法修复。
