# ADR-0006：Android 定位为瘦客户端 + 本地完整数据副本

- **Status**: Accepted
- **Date**: 2026-10-13
- **Supersedes**: —

## Context

需求方最初的设想是「各端都是算力节点」。但 Android 上有两个独立的障碍：

**障碍一：pi 需要 Node.js ≥ 22.19，而 Android 上没有原生 Node 环境。**

可行路径只有两条：

| 路径 | 说明 |
| --- | --- |
| 内置 `nodejs-mobile` | 把 Node 运行时打进 APK，可跑真 agent。代价：包体显著增大、上游维护不活跃、崩溃率上升 |
| 不跑 pi，做瘦客户端 | Android 只做 UI + 通知 + 本地数据副本，agent 执行交给其他节点 |

（Termux 是官方验证过的路径，但它要求用户手动安装 Termux、执行命令行操作，与「安装即用」直接冲突，因此不作为产品路径。）

**障碍二：Android 的后台执行限制是操作系统设计，不是可绕过的工程问题。**

Doze 模式、后台服务限制、以及各厂商的激进杀后台策略，使得一个长期驻留的 agent 进程无法保证存活。这意味着即使内置了 Node，Android 也无法承担「常驻算力节点」的角色。

## Decision

**Android 定位为瘦客户端**，具体含义：

- ✅ 持有**完整的结构化数据副本**（笔记、日程、待办、会话记录）——满足全量复制的要求
- ✅ 可**离线读写**本地数据，无需任何节点在线
- ✅ 可**接收与触发提醒**（通过系统级闹钟，不依赖 agent 常驻）
- ✅ 可发起对话请求（需要算力节点在线）
- ❌ **不执行 agent**，不运行 pi
- ❌ 不承担常驻角色

## Consequences

**正面**

- 交付风险最低：不需要与 nodejs-mobile 的兼容性、包体、崩溃率搏斗
- Android 端体验更好：启动快、省电、不会被系统杀死导致功能异常
- 数据可用性与算力可用性解耦，行为可预测——用户离线时仍能看到全部数据
- 与「全量复制」决策天然兼容

**负面**

- **与需求方最初「各端都是算力节点」的设想有出入**。当所有算力节点都关机时，Android 无法执行 agent，只能读写数据
- 需要一套「算力节点不可用」的降级体验设计：请求排队？明确提示？还是允许稍后重试？
- Android 端必须实现完整的 CRDT 合并逻辑（因为它要能离线写入），这部分代码量与桌面端相同
- 会话的实时流在 Android 上需要通过其他节点转发，增加了协调层的职责

## Alternatives considered

**内置 nodejs-mobile** — 能实现真正的本地自治。被否决，主要原因不是包体，而是**即使内置了 Node，后台限制依然存在**——用户锁屏一段时间后进程仍会被杀，所谓「算力节点」名不副实，却要付出明显的维护成本。

**Android 只做纯 UI，不留数据副本** — 实现最简单。被否决：与「全量复制」和「任一台关闭不影响整体」的要求冲突，且离线时 App 完全不可用。

## 备注

本决策**不影响** Android 端的数据层实现——它仍需完整实现 op log、CRDT 合并、墓碑等机制（见 [data-model.md](../data-model.md)）。瘦客户端指的是「不跑 agent」，不是「不参与同步」。
